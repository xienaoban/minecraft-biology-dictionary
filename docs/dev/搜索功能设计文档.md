# 生物辞典搜索功能：需求分析与设计

> 状态：草稿（分支 `dev-search`，基于 `main-26.3` / mod v1.3.2 / MC 26.3）。需求与设计由作者补充；"现状梳理"、"开放问题"、"待设计块清单"为辅助调研。

## 1. 背景与目标

（待补充：动机与目标的正式表述）

当前实体列表只能靠"全部实体"书签或标签目录逐页翻找，模组环境下实体类型可达上千，定位某个生物的成本很高。本特性为生物辞典增加检索能力，作为与书签并列的独立入口。

## 2. 需求分析

### 2.1 功能需求

| # | 需求 | 说明 |
| --- | --- | --- |
| FR1 | 搜索入口按钮 | 位于 `AbstractBiologyDictionaryScreen` 书本**右侧、书页之外**，与左侧那排突出在书本外的书签镜像对称（自 `pageTop` 起沿竖直方向排列，突出书页外）；**不复用 `Bookmark` 体系**，是独立元素。美术资源后续提供，先以线条/平涂框占位 |
| FR2 | 独立搜索界面 | 基于 `AbstractBiologyDictionaryScreen` 新建独立 screen，可从来源界面进入并返回 |
| FR3 | 原版输入框 + 焦点输入 | 使用 MC 现成的 `EditBox`；仅当输入框获得焦点时可输入；进入搜索界面时焦点默认落在输入框上 |
| FR4 | 回车/按钮才检索 | 输入过程不实时过滤，按回车或点右侧搜索按钮才执行检索 |
| FR5 | 检索选项 | 三个开关照旧：全词匹配、区分大小写、正则。高级模式下它们只作用于"被匹配的文本"，即前缀引号内的值（`tag:"xxxx"` 里的 `xxxx`）以及等价于 `name:` 的裸词；正则不做全局匹配 |
| FR6 | 输入框独立于二次缩放 | 输入行使用原版屏幕坐标，不参与本模组的 `screenScale` 二次缩放；固定在书本材质之上；若缩放导致越出屏幕上沿，则贴屏幕上沿显示 |
| FR7 | 高级搜索模式 | 严格表达式语法：`&&`、`\|\|`、`!`、`()`，优先级 `!` > `&&` > `\|\|`。前缀的值**必须用英文双引号**括起，例：`tag:"minecraft:xxx" && (name:"Zombie.*" \|\| !(biome:"*:*sea"))`。引号同时解决值中的空格与 `&`、`\|`、`!` 等字面字符。**裸词等价于 `name:"词"`**，多个裸词之间是隐式 `&&`（`Zombie Villager` = `name:"Zombie" && name:"Villager"`）。不支持 `AND`/`OR`/`NOT` 或中文词，也不做全角标点兼容 |
| FR8 | 简单搜索模式 | 模糊搜索：输入框内容按空格分词，其余字符（含冒号）都是字面量，在"参与搜索的字段集合"上做模糊匹配；用户不需要任何语法 |
| FR9 | 字段前缀（仅高级模式） | 前缀按"id 形态 / 名字形态"成对出现：`tag:` / `tagName:`、`class:` / `className:`、`biome:` / `biomeName:`、`structure:` / `structureName:`、实体的 `id:` / `name:`，另有 `discovered:`；值一律写成 `前缀:"值"` |
| FR10 | 结果分页展示 | 搜索结果用现有 `Page` 网格展示；未执行检索时（含刚进入界面）显示全部生物 |
| FR11 | 结果区工具条复用主页 | 结果区右上角提供与主页相同的按钮（仅已发现过滤、多选/选择模式、选择计数等） |
| FR12 | 左侧书签复用为分类入口 | 书签顺序与主页相近（返回主页、各分类书签），但**不显示设置与关于**；除主页已有的分类外，还支持**按群系、按结构**分类。点书签仍进入该分类的 `Catalog` 列表 |
| FR13 | 目录条目的操作方式 | **不使用左右键语义**。条目本体点击用于进入下级（预览）；鼠标悬浮到条目上时，条目右侧出现两个并排按钮：写入该条目的 **id**、写入该条目的**当前语言名字**（分别对应 `tag:"..."` 与 `tagName:"..."` 这类前缀）。按钮不配 tooltip（靠按钮本身表意）。不设勾选状态，输入框是条件的唯一真相 |
| FR14 | 群系/结构索引懒加载 | 群系/结构的全量索引由服务端下发；**懒加载**，不在一进游戏/进世界时就下载；具体触发时机待定 |
| FR15 | （未来）检索结果保存为分类 | 把某个检索条件的**结果集**保存为"默认"分组（`defaultTags`）下的一个新分类，之后可像普通分类一样浏览与进入 |
| FR16 | 简单模式的字段勾选 | 简单模式下可勾选"参与搜索的字段"（要搜哪些、不搜哪些前缀）；默认 `name` / `class` / `id` |
| FR17 | 双模式切换 | 切换模式时**直接清空输入框**；两种模式各自保存自己的字符串（含简单模式的字段勾选态），切回时恢复各自的串。因此不需要做无损转换；暂不给提示，后续再议 |
| FR18 | `name` 的跨语言检索 | `name` 匹配当前语言 + 英文 + 中文（`name` 字段，两种模式都适用）；实现成本见 §5.4 |
| FR19 | 目录可展开到生物列表 | 书签分类可逐级展开（分类 -> 子分类 -> 生物列表），点击条目本体即进入下一级列表 |
| FR20 | 生物卡片的按钮 | 搜索界面的生物卡片**不提供详情与高亮**；鼠标悬浮时在卡片内**上下**出现两个按钮：写入该生物的 **id**、写入该生物的**当前语言名字**（分别对应 `id:"..."` 与 `name:"..."`）。按钮不配 tooltip；卡片本体点击行为待定（§4） |

> 注：`discovered:` 前缀与右上角"仅已发现"按钮语义重复，暂时保留。它是"检索条件"这一层的明确语义，且 FR15 需要条件可序列化，前缀形式比界面开关更适合作为持久化形式。

### 2.2 非功能需求

- **条件可序列化、可往返**：高级模式的查询串是条件的主要序列化形式；未来 FR15 要把条件存成分类，因此语法必须稳定，且"解析 -> 打印"应幂等（点击目录条目生成的串必须能被重新解析成同一条件）。
- **模式隔离**：切换模式会清空输入框，两种模式各自暂存自己的串，见 FR17 与 §5.1。
- 性能、兼容、多语言文案等见 §4、§5。

## 3. 现状梳理

### 3.1 主界面与实体列表

- 主界面 `BdHomeScreen` 是实体列表的唯一入口，书签分两类：`AllEntitiesBookmark`（全部实体）与每个 `TagGroup` 一个 `TagGroupBookmark`；`TagGroupBookmark` 进入的是标签目录（`TagCatalog`），点某个 `Tag` 后才列出该标签下的实体。
- 实体列表数据来自 `EntityManager`：全部实体为 `getEntityEntries()`，标签内为 `Tag#getEntities()`；元素类型为 `EntityDictionaryEntry`，携带 `EntityType<?>`、可选实体类、`Identifier`、`namespace:path` 字符串 ID、`sortId`（排序号）。
- 列表按 `Page`（9 行 × 8 列）分页渲染，`resetAndAddEntityWidgets` 负责重建卡片、刷新左右/右上工具条并重置页码。
- 每个卡片显示实体名（`EntityUtils.getEntityTypeNameText`，即当前客户端语言的翻译名）；未发现实体显示 `??`，且 `BdEntityOverviewScreen.canOpen` 会拦住非创造模式的未发现实体。

### 3.2 书签与"右上角"的现有占用

- 书签在 `AbstractBiologyDictionaryScreen` 里是长度 10 的 `Bookmark[]`，位置由 `resizeBox` 统一摆在**书本左侧、书页之外**（`leftPageLeft(width) - box.getWidth() - 19`），自上而下竖排、悬浮时向左外滑一格（`offsetL = hovered ? W : 0`）；`Bookmark` 是 `ScreenElement` 的子类，走二次缩放坐标系。
- 书签格高 `Widget.WIDGET_HEIGHT`(10) + 4 = 14，10 个约占 136px，而可用竖向空间约 `BOOK_HEIGHT`(192)；主页现在用掉 8 个（关于、设置各占末尾一个，全部实体 1 个，5 个 `TagGroup`）。FR12 的 8 个书签（返回主页 + 5 分组 + 群系 + 结构）同样放得下，再增分组就接近上限。
- FR1 的搜索按钮是书签的右侧镜像：贴在右页右缘之外（可参照 `rightPageLeft(width) + Page.PAGE_WIDTH + 19`），纵向从 `pageTop(height)` 起按 `box.getHeight() + 4` 递增；`resizeBox` 是统一的布局入口。
- `BdHomeScreen.upperRightToolBar`（"仅已发现"过滤器/选择模式按钮）位于**书本内部右页上沿之外**，与书外右侧的搜索按钮不在同一区域，两者不冲突。
- 现有按钮风格参考 `gui/component/LongButton`：平涂矩形 + 悬浮提亮，注释里已注明"美术就绪后换贴图"，与 FR1 的占位需求一致。

### 3.3 列表视图的整体复用（已定：抽成共享）

主页的列表视图相关实现目前**全部是 `BdHomeScreen` 的私有成员**，搜索界面要复用（FR10、FR11、FR13）就得先抽出来：

- 取数与卡片：`getEntityWidgets`、`EntityCardWidget`、`EntityActionCardWidget`、`EntitySelectionCardWidget`。
- 工具条：`createUpperRightButtons`、`DiscoveredEntityFilterButton`、`EntitySelectionModeButton`、`EntitySelectionCountDisplay`、`AddToBlacklistButton`，以及 `DiscoveryProgressWidget`、`DecorativeBarWidget`、`setToolBars` 与 `resizeBox` 里的工具条布局。
- 选择模式（进入/退出、选中集合、黑名单动作）也都在 `BdHomeScreen` 内部。
- 已定方案是抽成共享位置；具体形态（公共基类还是独立组件类）、抽到哪一层（`gui/` 还是 `gui/component/`）未定。
- 两个界面的卡片行为不同：主页卡片左键进详情、右键高亮；搜索界面的卡片不带详情/高亮，动作是"写入检索框"一类。因此抽取时要拆成"公共卡片基类 + 两个具体卡片"，不能直接共用一个类。

其它既有机制：

- "仅已发现"是客户端内存态 `BiologyDictionaryClient.shouldShowOnlyDiscoveredEntities()`（初值取自客户端配置 `showOnlyDiscoveredEntitiesByDefault`），在 `getEntityWidgets` 里逐条过滤，切换时通过 `rebuildEntityWidgets(getCurrPageIndex())` 重建。
- 视图重建的现有模式是"整表重建 + 保留页码"（`resetAndAndWidgetsOneByOne` + `setCurrPage`），搜索结果分页可以复用这条路径。

### 3.4 原版 widget 的接入点（关键）

- 本模组目前**没有任何原版 `AbstractWidget` 的使用**，`screen.addRenderableWidget` 尚未出现过。
- `AbstractBiologyDictionaryScreen#resize()` 里已留好注释 `// Add some vanilla-widgets here.`，即作者预留的接入点；`CommonScreen#init()` 是 final 的，`Screen#rebuildWidgets()` 会先 `clearWidgets()` 再 `init()`，因此在 `resize()` 里挂 widget 不会重复累积。
- 原版 widget 由 `CommonScreen#afterRender` 在 `scaleToOriginalOnce()` 下经 `super.extractRenderState(...)` 绘制，即**原始屏幕坐标系**，天然不受二次缩放影响，与 FR6 一致；代价是它画在自定义元素之上，且与书本贴图的相对位置只能按原始坐标估算。
- 命中测试也是分开的：`CommonScreen#mouseClicked` 先用二次缩放后的坐标给自定义元素，未被消费时才把原始 `MouseButtonEvent` 交给 `super.mouseClicked`，原版 widget 拿到的正是原始坐标。

### 3.5 文本输入与键盘事件（关键约束）

- `EditBox#setResponder(Consumer<String>)` 是在**每次文本变化**时回调的，不是回车回调；MC 26.3 的 `EditBox#keyPressed` 只处理删除/方向键/全选/复制/粘贴/剪切/Home/End，**不消费回车**；原版 `Screen#keyPressed` 也不处理回车。所以 FR4 的"回车才检索"必须在 `screen#keyPressed` 里自己判断回车键（或自建回调），不能直接用 `setResponder`。
- `Screen#setInitialFocus()` 仅在"上一次输入类型是键盘"时才自动聚焦第一个可聚焦 widget（手柄/纯鼠标操作不会自动聚焦），FR3 的"默认聚焦"需注意这一前提。
- 输入法（IME）：`EditBox` 实现了 `charTyped` 与 `preeditUpdated`，原版派发链路可以正常走通；本模组的 `CommonScreen`/`ElementScreen` 都没有覆盖 `charTyped`，所以只要焦点在原版 widget 上，中文输入法即可工作。
- **冲突**：`AbstractBiologyDictionaryScreen#keyPressed` 目前在按下 `KeyMappings.OPEN_HANDBOOK`（反引号）或 `client.options.keyInventory`（E）时直接 `onClose()`。原版 `Screen#keyPressed` 是"先给子类，再给当前焦点 widget"，所以在输入框聚焦时打字 `e` 会先关屏。FR3 落地时必须先在 `keyPressed` 里让位于输入焦点。
- `ElementScreen` 的自定义元素体系只有鼠标（`ScreenElement#mouseDown`），没有焦点/键盘概念，因此输入框本身无法套用自定义元素框架。

### 3.6 名称与别名的可用来源

- 当前语言显示名：`EntityType#getDescription()`（`EntityUtils.getEntityTypeNameText` 直接返回它）。
- **英文名**：`net.minecraft.locale.Language.DEFAULT_INSTANCE` 只加载原版内置的 `assets/minecraft/lang/en_us.json`，不含模组实体。
- **中/英文名（FR18 可行性）**：模组实体的其他语言名要自己读。`Minecraft#getResourceManager()` 提供 `getNamespaces()` 与 `getResource(Identifier)`，`Resource#open()` 拿到流后可直接用 `net.minecraft.locale.Language.loadFromJson(InputStream, BiConsumer)` 解析。做法是只对"有实体类型的命名空间"读 `assets/<ns>/lang/en_us.json` 与 `zh_cn.json`，按实体的 descriptionId 取出所需值后丢弃整张 map，内存只多出"实体数 x 2 个字符串"；缺失的语言文件要能优雅回退到当前语言名。退一步的零成本近似是用翻译 key 尾段（`entity.<ns>.<path>` 的 path 转空格），但与真实显示名不完全一致。
- 稳定标识：`Identifier`（`namespace:path`）、翻译 key；类名可用 `EntityManager.getClassRealName`（26.x 不混淆），但 `EntityDictionaryEntry#getClazz()` 可能为空（无对应实体类的类型）。
- 群系/结构的显示名同样是翻译 key：`biome.<ns>.<path>`、`structure.<ns>.<path>`。
- **分类（`Tag`）的显示名来自翻译，且模组自带了原版那部分的翻译**：`Tag` 构造里 `text = TextUtils.translate(name)`，即 `name` 本身就是翻译 key。模组的 lang 文件确实为原版内容提供了条目——MC 标签用 `Identifier#toLanguageKey()`（冒号换点，如 `minecraft.zombies`）、类与接口用全限定类名（如 `net.minecraft.world.entity.Entity`）、结构用 `structure.<ns>.<path>`，各自都有中英文。
- **模组新增的标签/类没有翻译**（谁也无法预先翻译别人的模组），`Component.translatable` 会原样回退成 key 本身（如 `create.something`），可用 `TextUtils.hasTranslation` 判断。
- **key 形态与查询形态不同**：`Tag.name` 是点分形态（`minecraft.zombies`），而查询语法里写的是带冒号的 id（`tag:"minecraft:zombies"`），索引与解析之间需要一层映射。
- 可用的分类数据源：标签走 `EntityManager.Tag`/`TagGroup`（现有 5 个分组：默认、MC 标签、模组、类、接口）；已发现走 `ClientDiscoveryCacheManager#isDiscovered`；群系与结构走 `EntitySpawnManager`（见 §3.8 的可用性限制）。
- 别名目前只有一处先例且仅针对物品：`compat/jei/BiologyDictionaryJeiPlugin` 给辞典书本注册了 `"生物辞典" / "Biology Dictionary" / "shengwucidian"` 三个 JEI 搜索别名。实体侧没有别名注册表，也没有拼音数据源（本次范围外）。

### 3.7 客户端/服务端边界

- 实体列表、发现缓存、标签分类、"仅已发现"开关全部在客户端，因此基于这些数据的过滤不需要任何网络包，也不改动服务端配置/发现策略。
- 群系/结构是例外，见 §3.8。

### 3.8 群系/结构数据的客户端可用性（关键阻塞点）

- `EntitySpawnManager` **只挂在 `ServerWorldSession`**，构造时用 `server.registryAccess()`（需要 WORLDGEN 层注册表）并对结构模板做分析，是纯服务端设施；`ClientWorldSession` 上没有任何对应实例。
- 客户端目前只能**按单个实体类型、按需**拿到生成信息：`EntitySpawnManager` 的读写封装在 `MobSpawnProperty`，其 `getFrom` 直接 `ServerWorldSession.get()`，客户端为 null 即置空；数据实际通过 `RequestEntityOverviewPacket` -> `SendEntityOverviewPacket`（`EntityOverviewCache`）在打开某个生物的详情页时同步过来。
- 客户端**没有"全部群系/结构 -> 实体集合"的全局索引**：`EntitySpawnManager#getBiomeEntities` 是反查 Map，只有服务端持有。`SpawnMap` 也只在内部维护 forward/reverse 两个 Map，未暴露键集合。
- 结论：FR9 的 `biome:`/`structure:` 检索与 FR12 的群系/结构书签筛选，都需要新增数据通道。**方向已定**（FR14）：由服务端下发全量索引、客户端懒加载，不在进游戏/进世界时下载；触发时机与协议细节待定（见 §5.5）。

## 4. 开放问题（待作者决策）

1. **搜索按钮的位置细节**：镜像书签时是"整个按钮在书页外"还是"一半压在书页上"？左侧书签悬浮时向左外滑，右侧按钮是否镜像向右滑出？目前只有这一个按钮，"竖排"是否意味着以后还会有更多贴边按钮共用这一列（需预留排布规则）？按钮文字是横排还是旋转竖排？哪些子类显示该按钮，搜索界面自身是否显示？
2. **结果页的其余细节**：结果沿用 `Page` 网格、初始显示全部生物已定；是否显示命中数量与空结果提示？点击卡片是否沿用现有"打开详情/创造模式可开未发现"的规则？返回键回到来源界面还是主界面？检索后是否重置到第 1 页、清空查询后是否恢复全部生物？

## 5. 尚未展开的设计块（待细化）

> 已经成型的部分见 §2（需求）与 §6（设计）；下列是还需要设计、目前只有零散约束的大块。

### 5.1 条件模型（双模式）

**简单搜索模式**

- 输入是一串关键词，按空格分词（空格即分词器）；其余字符（冒号、`&`、`|`、`!`、括号）都是普通字面量，不需要也不支持转义。
- 在"参与搜索的字段集合"上做模糊匹配，集合由输入行旁的勾选决定（FR16），默认 `name` / `class` / `id`。
- 没有 AST，也不存在语法错误。

**高级搜索模式**

- 输入是一个表达式，解析成条件 AST：`&&`、`||`、`!`、`()`，优先级 `!` > `&&` > `||`。
- 前缀写法固定为 `前缀:"值"`，冒号后必须紧跟英文双引号，值以引号定界，因此值里的空格、冒号、`&`、`|`、`!` 都不需要额外规则。
- 值以引号定界后，原先"按第一个冒号切分"的规则作废（更简单，也不再需要）。
- 字段名不在已知前缀表里按语法错误处理（高级模式严格），不退回关键词。
- **裸词等价于 `name:`**：`Zombie Villager` 等价于 `name:"Zombie" && name:"Villager"`（空格即隐式 `&&`）。因此高级模式下裸词只搜 name，其它字段必须显式写前缀。
- 三个开关（全词匹配 / 区分大小写 / 正则）同样作用于裸词。

**两种模式的关系**

- 同一时刻只有一个模式生效，输入框始终只有一份文本，因此仍是"单一真相"。
- **切换模式直接清空（FR17）**：两种模式各自保存自己的输入串（以及简单模式的字段勾选态），切走时把当前串存进该模式的槽位并清空输入框，切回时从槽位恢复。因此不存在"重解释已有文本"的问题，也不需要无损转换。
- 简单模式的字段勾选态同样按模式各自保存。

**目录条目与卡片的操作**

- 不用左右键语义：条目**本体点击** = 进入下级（预览，FR19）；**悬浮**到条目上时右侧出现两个并排按钮，分别写入 id 形态（`tag:"minecraft:zombies"`）与名字形态（`tagName:"僵尸"`）的条件。
- 生物卡片同理：悬浮时卡片内上下两个按钮，写入 `id:"..."` 与 `name:"..."`（FR20）。
- 按钮写入的都是**高级模式条件**，所以在简单模式下会先切到高级模式（简单串暂存并清空）再追加。
- 写入的具体行为（插入位置、是否补 `&&`、是否加括号、是否去重、是否立即检索）见 §4。

**取舍记录**：曾考虑"勾选分类作为隐式条件"，因"同一件事两个入口"更乱而放弃；`discovered:` 与右上角按钮语义重复但仍保留（明确的检索语义 + 为 FR15 铺路）。

**仍需补充**：当前生效条件如何展示与清除、是否持久化。

### 5.2 高级模式的词法与错误反馈

- 词法：`前缀` + `:` + 英文双引号定界的值。值内部的引号用 **JSON 风格转义**（`\"`）；反斜杠本身是否也要写成 `\\` 待定。
- 三个开关（全词匹配 / 区分大小写 / 正则）作用于前缀引号内的值，也作用于裸词；都不是全局开关。
- 简单模式没有词法层：按空格分词后直接做模糊匹配，无错误态。
- 全角标点不做兼容，`AND`/`OR`/`NOT` 与中文词也不支持（作者定：走高级模式的默认是程序员）。
- 错误反馈：引号不配对、括号不配对、未知前缀、悬空运算符（`a&&`、`&&a`、`!!a`）、空表达式，如何提示（提示行 / 标红 / 不执行）。
- 是否提供前缀与取值的提示、自动补全；是否需要查询历史。

### 5.3 结果排序与命中反馈

- 结果保持词典序（`sortId`）还是按相关度排序。
- 命中片段是否高亮；命中计数与空状态的呈现。

### 5.4 索引构建与生命周期

- 默认字段索引（name / class / id）何时建、放在哪：按仓库约定应挂 `ClientWorldSession`/`WorldSession`，而不是散落的 static。
- `name` 的跨语言索引（FR18）：只对有实体类型的命名空间读 `assets/<ns>/lang/en_us.json` 与 `zh_cn.json`，原版英文名可直接白嫖 `Language.DEFAULT_INSTANCE`。首次构建有一次性资源读取与 JSON 解析开销，需要决定是否异步、以及首次构建的触发点。
- 索引内容：每个实体保留 当前语言名 / 英文名 / 中文名 / id / 类名 的小写化形式，供两种模式共用。
- 分类条目索引：每个 `Tag` 存"原始 `name`（点分 key / 全限定类名 / 命名空间）+ 当前语言显示名"，并额外用 lang 文件补英文与中文（`name` 就是翻译 key；原版那部分模组自带翻译，模组内容多半没有，靠 `TextUtils.hasTranslation` 判断后回退）；群系/结构同理（`biome.<ns>.<path>` / `structure.<ns>.<path>`）。查询串里的冒号 id 与内部的点分 key 之间需要一层映射。
- 切换语言、资源包重载、重新连接后索引如何失效与重建。
- 性能预算：是否缓存小写化字符串、是否避免重复构建 `Component`。

### 5.5 群系/结构索引的网络协议（最大新增块）

- 方向已定：服务端全量下发 + 客户端懒加载，不在进世界时下载（FR14）；触发时机仍待定（§4 第 6 条）。

- 加载态的界面反馈、失败/超时/重试；单人模式下的路径；服务端是否提供配置开关与权限；索引是否落盘缓存；协议向后兼容。
