# 生物辞典搜索功能：需求分析与设计

> 状态：设计稿（分支 `dev-search`，基于 `main-26.3`、mod v1.3.2、MC 26.3）。§4 是已定设计，§5 是尚待决策的问题。

## 1. 背景与目标

生物辞典的实体列表目前只能靠"全部实体"书签和标签目录逐页翻找，模组环境下实体类型可达上千，定位某个生物的成本很高。本特性给辞典增加一个与书签并列的检索入口：

- **简单搜索**面向普通玩家：不需要任何语法，往输入框里输入关键词即可；
- **高级搜索**面向进阶玩家：完整的布尔表达式与字段前缀；
- 分类入口复用现有书签体系，可从分类一路下钻到生物，并把条目的 id 或名字一键写进检索式；
- 群系、结构等分类数据只有服务端持有，需要新增下发通道。

## 2. 需求

### 2.1 功能需求

| --- | --- | --- |
| FR1 | 搜索入口按钮 | 位于书本**右侧、书页之外**，与左侧那排突出在书本外的书签镜像对称（自 `pageTop` 起竖排、突出书页外）；不复用 `Bookmark` 体系，是独立元素。美术资源后补，先以线条/平涂框占位 |

| FR6 | 双模式 | 简单搜索与高级搜索两种模式，界面上可切换 |

| FR8 | 简单模式的字段勾选 | 可勾选要搜哪些、不搜哪些字段；默认 `name` / `class` / `id` |
| FR9 | 高级搜索模式 | 表达式 `&&`、`\|\|`、`!`、`()`，优先级 `!` > `&&` > `\|\|`；前缀的值必须用英文双引号定界；**裸词等价于 `name:"词"`**，多个裸词之间是隐式 `&&`。不支持 `AND`/`OR`/`NOT`、中文词与全角标点 |
| FR10 | 字段前缀 | 按"id 形态 / 名字形态"成对：`tag:` / `tagName:`、`class:` / `className:`、`biome:` / `biomeName:`、`structure:` / `structureName:`、实体的 `id:` / `name:`，另有 `discovery:`；一律写成 `前缀:"值"` |
| FR11 | 检索选项 | 三个开关：全词匹配、区分大小写、正则，**默认全部关闭**，简单模式同样保留正则。高级模式下它们作用于前缀引号内的值与裸词，不是全局开关 |
| FR12 | 模式切换 | 切换时清空输入框；两种模式各自暂存自己的串（含简单模式的字段勾选态），切回时恢复。暂不给提示 |
| FR13 | `name` 的跨语言检索 | `name` 匹配当前语言 + 英文 + 中文；实现见 §4.7 |
| FR14 | 结果分页展示 | 结果用现有 `Page` 网格展示；未执行检索时（含刚进入界面）显示全部生物，检索后显示命中的生物 |
| FR15 | 结果区统计 bar | 用一个新的 bar（如"检索到 xx 个生物"）替换主页那对左右工具条 |
| FR16 | 左侧书签复用为分类入口 | 顺序与主页相近（返回主页 + 各分类书签），但不显示设置与关于；除主页已有分类外，增加按群系、按结构分类 |
| FR17 | 目录可下钻 | 分类可逐级展开（分类 -> 子分类 -> 生物列表），点击条目本体进入下一级 |
| FR18 | 目录条目的操作 | 不使用左右键语义。条目本体点击进入下级；鼠标悬浮到条目上时，**叠加**显示两个并排按钮，分别写入该条目的 id 与当前语言名字（对应 `tag:"..."` / `tagName:"..."` 这类前缀）。按钮不加 tooltip |
| FR19 | 目录与目录内卡片的写入按钮 | **仅**搜索界面的分类目录条目、以及目录下钻出的生物卡片，悬浮时**叠加**显示两个写入按钮（id / 当前语言名字，如 `tag:"..."` / `tagName:"..."`、`id:"..."` / `name:"..."`）。按钮不加 tooltip；主页与检索结果的卡片没有这个功能 |
| FR20 | 群系/结构索引同步 | 进入世界时用一个独立请求向服务端索取群系/结构索引；生物到群系的映射重复字符串很多，直接压缩后传输；客户端不落盘；请求失败则该维度无法检索，并在输入框下报错 |
| FR21 | 结果页卡片交互 | 检索结果（以及默认的"全部生物"）沿用主页卡片逻辑：点击打开详情、右键高亮等，不存在写入 id 的诉求 |
| FR22 | （未来）检索结果保存为分类 | 把某个检索条件的**结果集**保存为"默认"分组（`defaultTags`）下的一个新分类，之后可像普通分类一样浏览与进入 |

> `discovery:` 与右上角"仅已发现"按钮语义重复，仍然保留：它是"检索条件"这一层的显式表达，且 FR22 需要条件可序列化，前缀形式比界面开关更适合作为持久化形式。

### 2.2 非功能需求

- **条件可序列化、可往返**：高级模式的查询串是条件的主要序列化形式。FR22 要把它存成分类，因此语法必须稳定，"解析 -> 打印"应幂等（目录按钮生成的串必须能被重新解析成同一条件）。
- **模式隔离**：两种模式各自持有一份输入与选项，互不干扰（FR12）。
- 性能、兼容、多语言文案等见 §5。

### 2.3 范围外（明确不做）

- 实体搜索别名的注册接口（作者明确"先算了"）。
- FR22"检索结果保存为分类"本次只记录、不实现。

## 3. 现状梳理

### 3.1 主界面与实体列表

- 主界面 `BdHomeScreen` 是实体列表的唯一入口。书签分两类：`AllEntitiesBookmark`（全部实体）与每个 `TagGroup` 一个 `TagGroupBookmark`；后者进入标签目录（`TagCatalog`），点某个 `Tag` 后才列出该标签下的实体。
- 列表数据来自 `EntityManager`：全部实体为 `getEntityEntries()`，标签内为 `Tag#getEntities()`。元素类型 `EntityDictionaryEntry` 携带 `EntityType<?>`、可选实体类、`Identifier`、`namespace:path` 字符串 ID 与 `sortId`（排序号）。
- 列表按 `Page`（9 行 × 8 列）分页渲染，`resetAndAddEntityWidgets` 负责重建卡片、刷新左右/右上工具条并重置页码。
- 卡片显示实体名（`EntityUtils.getEntityTypeNameText`，即当前客户端语言的翻译名）；未发现实体显示 `??`，且 `BdEntityOverviewScreen.canOpen` 会拦住非创造模式的未发现实体。

### 3.2 书签布局与"右上角"

- 书签是 `AbstractBiologyDictionaryScreen` 里长度 10 的 `Bookmark[]`，由 `resizeBox` 统一摆在**书本左侧、书页之外**（`leftPageLeft(width) - box.getWidth() - 19`），自上而下竖排，悬浮时向左外滑一格。`Bookmark` 是 `ScreenElement` 子类，走二次缩放坐标系。
- 每格高 `Widget.WIDGET_HEIGHT`(10) + 4 = 14，10 格约占 136px，可用竖向空间约 `BOOK_HEIGHT`(192)。主页现在用掉 8 格（关于、设置各占末尾一格，全部实体 1 格，5 个 `TagGroup`）。FR16 的 8 格（返回主页 + 5 分组 + 群系 + 结构）同样放得下，再增分组就接近上限。
- FR1 的搜索按钮是书签的右侧镜像，可参照 `rightPageLeft(width) + Page.PAGE_WIDTH + 19`，纵向从 `pageTop(height)` 起按 `box.getHeight() + 4` 递增；`resizeBox` 是统一的布局入口。
- `BdHomeScreen.upperRightToolBar`（仅已发现过滤器、选择模式按钮）位于**书本内部右页上沿之外**，与书外右侧的搜索按钮不在同一区域，两者不冲突。
- 现有按钮风格参考 `gui/component/LongButton`：平涂矩形 + 悬浮提亮，注释里已注明"美术就绪后换贴图"，适合作为 FR1 的占位。

### 3.3 列表视图需要抽成共享

主页的列表视图实现目前**全部是 `BdHomeScreen` 的私有成员**，搜索界面复用前必须先抽出来：

- 取数与卡片：`getEntityWidgets`、`EntityCardWidget`、`EntityActionCardWidget`、`EntitySelectionCardWidget`。
- 工具条：`createUpperRightButtons`、`DiscoveredEntityFilterButton`、`EntitySelectionModeButton`、`EntitySelectionCountDisplay`、`AddToBlacklistButton`，以及 `DiscoveryProgressWidget`、`DecorativeBarWidget`、`setToolBars` 与 `resizeBox` 中的工具条布局。
- 选择模式的进入/退出、选中集合、黑名单动作也都在 `BdHomeScreen` 内部。
- 卡片分两类：主页与**结果视图**用"左键详情、右键高亮"的卡片；**目录视图**（分类目录条目与目录下钻出的生物列表）用带写入按钮的卡片。抽取时要拆成"公共卡片基类 + 主页式卡片 + 目录写入卡片"。
- 抽取形态（公共基类还是独立组件类）与落点（`gui/` 还是 `gui/component/`）尚未定。

其它可复用的既有机制：

- "仅已发现"是客户端内存态 `BiologyDictionaryClient.shouldShowOnlyDiscoveredEntities()`（初值取自客户端配置 `showOnlyDiscoveredEntitiesByDefault`），在 `getEntityWidgets` 里逐条过滤，切换时用 `rebuildEntityWidgets(getCurrPageIndex())` 重建。
- 视图重建的既有模式是"整表重建 + 保留页码"（`resetAndAndWidgetsOneByOne` + `setCurrPage`），结果分页可以复用。

### 3.4 原版 widget 的接入点

- 本模组目前**没有任何原版 `AbstractWidget` 的使用**，`addRenderableWidget` 尚未出现过。
- `AbstractBiologyDictionaryScreen#resize()` 里已留好注释 `// Add some vanilla-widgets here.`；`CommonScreen#init()` 是 final 的，`Screen#rebuildWidgets()` 会先 `clearWidgets()` 再 `init()`，所以在 `resize()` 里挂 widget 不会重复累积。
- 原版 widget 由 `CommonScreen#afterRender` 在 `scaleToOriginalOnce()` 下经 `super.extractRenderState(...)` 绘制，即**原始屏幕坐标系**，天然不受二次缩放影响，与 FR3 一致；代价是它画在自定义元素之上，且与书本贴图的相对位置只能按原始坐标估算。
- 命中测试也是分开的：`CommonScreen#mouseClicked` 先用二次缩放后的坐标喂自定义元素，未被消费时才把原始 `MouseButtonEvent` 交给 `super.mouseClicked`，原版 widget 拿到的正是原始坐标。

### 3.5 文本输入与键盘事件的约束

- `EditBox#setResponder(Consumer<String>)` 是**每次文本变化**的回调，不是回车回调；MC 26.3 的 `EditBox#keyPressed` 只处理删除、方向键、全选、复制、粘贴、剪切、Home/End，**不消费回车**；原版 `Screen#keyPressed` 也不处理回车。所以"回车才检索"必须在 `screen#keyPressed` 里自己判断回车。
- `Screen#setInitialFocus()` 仅在"上一次输入类型是键盘"时才自动聚焦第一个可聚焦 widget（手柄或纯鼠标进入不会自动聚焦），FR4 的"默认聚焦"需注意这一前提。
- 输入法：`EditBox` 实现了 `charTyped` 与 `preeditUpdated`，且本模组的 `CommonScreen`/`ElementScreen` 都没有覆盖 `charTyped`，所以只要焦点在原版 widget 上，中文输入法即可正常工作。
- **冲突**：`AbstractBiologyDictionaryScreen#keyPressed` 目前在按下 `KeyMappings.OPEN_HANDBOOK`（反引号）或 `client.options.keyInventory`（E）时直接 `onClose()`；而原版派发顺序是"先给子类、再给焦点 widget"，所以在输入框里打字 `e` 会先关屏。落地时必须让位于输入焦点。
- `ElementScreen` 的自定义元素体系只有鼠标（`ScreenElement#mouseDown`），没有焦点与键盘概念，因此输入框无法套用自定义元素框架。

### 3.6 名称来源

- **实体**：当前语言显示名取自 `EntityType#getDescription()`（`EntityUtils.getEntityTypeNameText`）；id 为 `Identifier`（`namespace:path`）；类名可用 `EntityManager.getClassRealName`（26.x 不混淆），但 `EntityDictionaryEntry#getClazz()` 可能为空。
- **实体名的跨语言读取**（FR13 的依据）：`Language.DEFAULT_INSTANCE` 只加载原版内置的 `assets/minecraft/lang/en_us.json`，不含模组实体。模组实体的其它语言名要自己读——`Minecraft#getResourceManager()` 提供 `getNamespaces()` 与 `getResource(Identifier)`，`Resource#open()` 拿到流后可直接用 `net.minecraft.locale.Language.loadFromJson(InputStream, BiConsumer)` 解析。做法是只对"有实体类型的命名空间"读 `assets/<ns>/lang/en_us.json` 与 `zh_cn.json`，按实体的 descriptionId 取出所需值后丢弃整张 map，常驻内存只多出"实体数 x 2 个字符串"；缺失的语言文件要回退到当前语言名。
- **分类（`Tag`）**：`Tag` 构造里 `text = TextUtils.translate(name)`，即 `name` 本身就是翻译 key，显示名来自翻译。模组的 lang 文件确实为原版内容提供了条目——`net.minecraft.*` 155 条（类/接口的全限定类名）、`minecraft.*` 50 条（MC 标签的 `Identifier#toLanguageKey()`，冒号换点）、`structure.*` 34 条，各有中英文。
- **模组新增的标签/类没有翻译**（无法预先翻译别人的模组），`Component.translatable` 会原样回退成 key 本身（如 `create.something`），可用 `TextUtils.hasTranslation` 判断。
- **key 形态与查询形态不同**：`Tag.name` 是点分形态（`minecraft.zombies`），查询语法里写的是带冒号的 id（`tag:"minecraft:zombies"`），索引与解析之间需要一层映射。
- **群系/结构**：显示名同样是翻译 key（`biome.<ns>.<path>`、`structure.<ns>.<path>`），id 即 `<ns>:<path>`。
- **可用的分类数据源**：标签走 `EntityManager.Tag`/`TagGroup`（现有 5 个分组：默认、MC 标签、模组、类、接口）；已发现走 `ClientDiscoveryCacheManager#isDiscovered`；群系与结构走 `EntitySpawnManager`（可用性见 §3.8）。
- **别名**目前只有一处先例且仅针对物品：`compat/jei/BiologyDictionaryJeiPlugin` 给辞典书本注册了 `"生物辞典" / "Biology Dictionary" / "shengwucidian"` 三个 JEI 搜索别名。实体侧没有别名注册表，也没有拼音数据源（本次范围外）。

### 3.7 客户端/服务端边界

- 实体列表、发现缓存、标签分类、"仅已发现"开关全部在客户端，基于这些数据的过滤不需要任何网络包，也不改动服务端配置与发现策略。
- 群系/结构是唯一例外，见 §3.8。

### 3.8 群系/结构数据只在服务端

- `EntitySpawnManager` **只挂在 `ServerWorldSession`**：构造要用 `server.registryAccess()`（需要 WORLDGEN 层注册表）并分析结构模板，是纯服务端设施，`ClientWorldSession` 上没有对应实例。
- 客户端目前只能**按单个实体类型、按需**拿到生成信息：读写封装在 `MobSpawnProperty`，其 `getFrom` 直接取 `ServerWorldSession`，客户端为 null 即置空；数据实际经 `RequestEntityOverviewPacket` -> `SendEntityOverviewPacket`（`EntityOverviewCache`）在打开某生物详情页时同步过来。
- 客户端**没有"群系/结构 -> 实体集合"的全局索引**：`EntitySpawnManager#getBiomeEntities` 是反查 Map，只有服务端持有；`SpawnMap` 也只维护 forward/reverse 两个内部 Map，未暴露键集合。
- 因此 `biome:`/`structure:` 这类检索与群系/结构书签都需要新增数据通道，方案见 §4.8。

## 4. 设计

### 4.1 入口与导航

- 在 `AbstractBiologyDictionaryScreen` 上新增书本右侧、突出书页外的搜索按钮，与左侧书签列镜像对称，布局同样收在 `resizeBox` 里；不复用 `Bookmark` 基类与贴图，美术就绪前用线条/平涂框占位。初始位置参照 §3.2，尺寸细节由作者微调。
- 点击进入独立搜索界面（命名待定，形如 `BdSearchScreen extends AbstractBiologyDictionaryScreen`），记录来源界面以便返回。

### 4.2 搜索界面与输入行

- 输入行是一行四段：`[模式切换] [文本框] [三个开关] [检索]`，各部分高度一致，整体居中。
- **除文本框外都用原版组件**（原版按钮/开关类 widget），不再使用本模组的自定义 `ScreenElement`。
- 输入框用原版 `EditBox`，进入界面默认聚焦，只有聚焦时可输入。
- 这一行及其附属控件使用原版原始屏幕坐标，不参与 `screenScale` 二次缩放；固定在书本材质之上，越出屏幕上沿时贴屏幕上沿显示。
- 解析失败时，在输入框下方再悬浮一行红字（同样用原版组件、同样不参与二次缩放）。

### 4.3 双模式与查询语法

**简单搜索**

- 输入只是一串关键词，按空格分词；其余字符（冒号、`&`、`|`、`!`、括号）都是普通字面量，不需要也不支持转义。
- 在"参与搜索的字段集合"上做模糊匹配，集合由字段勾选决定，默认 `name` / `class` / `id`。
- 没有 AST，也不存在语法错误。

**高级搜索**

- 输入是表达式，解析成条件 AST：`&&`、`||`、`!`、`()`，优先级 `!` > `&&` > `||`。
- 前缀固定写作 `前缀:"值"`，冒号后必须紧跟英文双引号；值以引号定界，因此值里的空格、冒号、`&`、`|`、`!` 都不需要额外规则。
- 转义只支持 `\"` 与 `\\`。
- 裸词等价于 `name:"词"`，多个裸词之间是隐式 `&&`：`Zombie Villager` 即 `name:"Zombie" && name:"Villager"`。因此裸词只搜 name，其它字段必须显式写前缀。
- 边角规则：悬空或连续的运算符（`a&&`、`&&a`）按忽略处理，等价于 `&&`；空前缀值（`tag:""`）等于"全部"，即该字段不做限制；字段名不在已知前缀表里按语法错误处理。
- 例：`tag:"minecraft:xxx" && (name:"Zombie.*" || !(biome:"*:*sea"))`
- 不支持 `AND`/`OR`/`NOT` 与中文词，也不做全角标点兼容。

**模式切换**

- 同一时刻只有一个模式生效，输入框只有一份文本。
- 切换时清空输入框：两种模式各自暂存自己的输入串（以及简单模式的字段勾选态），切走时存进该模式的槽位，切回时从槽位恢复。暂不给提示。

**两种模式的差异是有意的**：简单模式的 `zombie` 会在勾选的字段集合上广撒网；高级模式的裸词 `zombie` 只等价于 `name:"zombie"`。

### 4.4 检索选项

- 三个开关：全词匹配、区分大小写、正则，默认全部关闭；简单模式同样保留正则。
- 高级模式下它们不是全局开关，只作用于"被匹配的文本"——前缀引号内的值，以及等价于 `name:` 的裸词；正则不做全局匹配。

### 4.5 列表视图与结果展示

- 搜索界面内部有两类列表视图，共用同一套 `Page` 网格与分页机制：
  - **结果视图**（默认）：显示全部生物或检索结果，卡片沿用主页逻辑（点击打开详情、右键高亮）。
  - **目录视图**：从左侧书签进入，可逐级下钻；条目与卡片带写入按钮，见 §4.6。
- 命中统计用一个新的 bar（如"检索到 xx 个生物"）替换主页那对左右工具条。
- 未执行检索时（含刚进入界面）显示全部生物；回车或点"搜索"后显示命中的生物。

### 4.6 目录视图：分类目录与写入按钮

- 左侧书签顺序与主页相近（返回主页 + 各分类书签），不显示设置与关于，并增加按群系、按结构分类；点书签进入该分类的 `Catalog` 列表。
- 不用左右键语义：条目**本体点击**进入下级，可逐级下钻到生物列表。
- 按钮**叠加**在条目/卡片之上（不挤占原有布局），大致位置先定，细节由作者微调。目录条目悬浮时显示两个并排按钮（写入 id / 写入当前语言名字）；下钻到的生物列表里，卡片悬浮时显示上下两个按钮（写入生物 id / 写入生物当前语言名字）。按钮都不加 tooltip。
- **写入规则**：若当前串尾不是 `&&` 或 `||`，自动补一个 `&&` 再追加；不自动加括号；表达式不做去重（检索结果本身天然去重）；写入后**不**自动检索，必须点"检索"。
  - 注意由此产生的优先级效果：在 `a||b` 后追加会得到 `a||b&&tag:"x"`，按优先级等价于 `a || (b && tag:"x")`。
- 按钮写入的都是高级模式条件，因此处于简单模式时会先切到高级模式（简单串暂存并清空）再追加。
- 不设勾选状态，输入框始终是条件的唯一真相。

### 4.7 检索索引

- 每个实体保留：当前语言名、英文名、中文名、id、类名的**小写化**形式，供两种模式共用。
- 跨语言名（FR13）：原版英文名可直接取自 `Language.DEFAULT_INSTANCE`；模组部分只对有实体类型的命名空间读 `assets/<ns>/lang/en_us.json` 与 `zh_cn.json`，取完即丢 map。
- 分类条目索引：每个 `Tag` 存原始 `name`（点分 key、全限定类名或命名空间）与当前语言显示名，并额外用 lang 文件补英文与中文。查询串里的冒号 id 与内部点分 key 之间需要一层映射。
- **名字形态的回退**：`xxName` 取不到名字时回退到 `xx` 的 id 形态（`tagName:` 回退 `tag:`、`className:` 回退 `class:`、`biomeName:` 回退 `biome:` 等）。原版那部分模组自带翻译，模组内容多半没有，靠 `TextUtils.hasTranslation` 判断。
- **类名匹配**：`class:` 做的是子串匹配，所以不开全词匹配时简单名（`Zombie`）天然能命中全限定名；没有实体类的类型搜不到，需要时可用 `!class:".*"`（配合正则开关）之类的写法。
- 按仓库约定，索引应挂在 `ClientWorldSession`/`WorldSession`，而不是散落的 static；切换语言、资源包重载、重新连接后需要失效重建。

### 4.8 群系/结构索引同步

- 数据来自服务端的 `EntitySpawnManager`；**进入世界时**用一个独立请求（不并与 config 之类的包混在一起）向服务端索取。
- 生物到群系的映射里有大量重复字符串，直接传体积偏大，因此**压缩后传输**（不给字符串赋 id，避免把传输格式搞复杂）。
- 客户端**不落盘**缓存。
- 请求失败时该维度无法检索，在输入框下用红字报错。
- 新包可参照现有的全量同步先例：`RequestBiologyDictionaryDiscoveryFullPacket` -> `ReplyBiologyDictionaryDiscoveryFullPacket`。
- 包体上限：26.3 原版自定义包为**客户端 -> 服务端 32767 字节、服务端 -> 客户端 1048576 字节**（`ServerboundCustomPayloadPacket` / `ClientboundCustomPayloadPacket` 的常量）。

## 5. 待决问题

**界面与交互**

1. **位置的最终微调**：FR1 搜索按钮与条目/卡片上的悬浮按钮，都只定了大致位置，尺寸与细节由作者调。
2. **写入后的反馈**：按写入按钮后停留原页还是跳回结果视图；写入后如何取消、"已写入"态如何显示（需要反解析输入串）。
3. **结果排序与命中反馈**：保持 `sortId` 词典序还是按相关度排序；命中片段是否高亮。
4. **结果区其余控件**：是否保留多选/加入黑名单，操作后结果是否立即重算；是否显示发现进度条与装饰条。
5. **导航状态机**：结果视图与目录视图的切换、书签高亮；返回主页书签、Esc、返回键三者行为是否一致；搜索界面自己的书签集合（去掉设置与关于后，其余是否都可点，是否保留"全部实体"）。
6. **状态生命周期**：查询串、开关、结果集、页码是否在"返回再进入"后保留；是否持久化进客户端配置。
7. **键盘与焦点**：输入框聚焦时屏蔽 E/反引号关屏的判定范围（只看 `isFocused()` 还是有文本才算）；Esc 是清空、取消焦点还是关屏；Tab/方向键是否用于切换焦点；纯鼠标进入时是否也强制聚焦。
8. **简单模式的字段勾选集合**：可勾哪些（name / class / id / tag / biome / structure / ...）；是否与高级模式的前缀表共用同一份定义。

**查询语法与匹配**

9. **前缀细节**：前缀名用 `discovery:` 还是早先写的 `discovered:`；名字形态的后缀式命名是否统一到所有维度；表里是否还需要一个独立的"生成"维度（与群系、结构并列）；值不带命名空间时（`tag:"zombies"`）按 path 宽松匹配还是要求全 id；是否支持通配（示例里的 `name:"Zombie.*"` 需要明确语义）。
10. **错误与提示文案**：红字提示的具体文案；是否提供前缀提示或自动补全、是否需要查询历史。

**数据与索引**

11. **实体名索引的构建时机**：FR13 的跨语言索引何时建、是否异步（首次读 lang 文件有一次性开销）；挂到 `ClientWorldSession` 的具体位置。
12. **群系/结构索引的剩余细节**：单人模式下的路径；服务端是否需要开关与权限；超时与重试策略；具体的压缩算法。
13. **群系/结构目录本身**：列出全部群系/结构还是只列有生成关系的；排序规则；完全没有生成数据的实体（如玩家、部分模组实体）如何归类；群系约 60+、结构约 30+，多页目录的翻页体验是否可接受。
14. **与发现系统的剩余细节**：三种 `discoveryStrategy`（`BIOLOGY_DICTIONARY` / `VANILLA_KILL` / `ALWAYS_UNLOCKED`）下的差异；"仅已发现"开关是共享主页的同一状态（`BiologyDictionaryClient` 内存态）还是独立状态。
15. **多人/服务端**：是否需要服务端配置开关或权限来禁用检索。
16. **性能**：实体类型上千时，回车触发的一次全量扫描是否够用，还是需要预建索引；是否限制结果数。
17. **FR22 的前置**：查询串要成为可持久化的分类定义，需要稳定的序列化格式与版本策略；且 `Tag`/`TagGroup` 目前每次进世界按注册表重建、没有任何持久化（`Tag` 的名字还兼作翻译 key），保存型分类需要自己的存储与重建注入。
18. **跨版本与双端范围**：本特性只落 26.3，还是要移植到其余 5 个版本目录。
