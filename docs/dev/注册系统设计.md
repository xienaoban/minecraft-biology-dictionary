# 注册系统设计

## 背景

widget、property、skill、entity order 四类注册项当前各自维护一套 `registerBuiltIn(Registrar)`。它的表面职责是“罗列内建注册项”，实际却混担了两个职责：

1. 初始化时把内建项写入各 registry 的内部 map；
2. 运行时被反复重走，换一个 `Registrar` 实现来“换个角度遍历全部项”——配置补全、测试校验、派生映射都依赖它。

前者是注册，后者是枚举。二者混在同一个可重入的代码块里，是后续一切问题的根源。

## 目标

1. 向第三方模组开放这四类注册项的注册；
2. 让“枚举全部项”与“执行注册逻辑”彻底解耦——枚举只读固化结果，注册只在生命周期内发生一次。

## 决策一：注册生命周期——收集一次，固化，运行时只读

re-walk 模式必须废止。重走 `registerBuiltIn` 意味着每次枚举都重新执行一遍注册逻辑。对内建项无所谓，但一旦开放给第三方，注册逻辑就可能包含耗时判断、对其他模组存在性的探测、甚至依赖运行时状态的分支。把这些逻辑放进运行时每次枚举，等于把第三方的开销摊到每一次配置 reload、每一次派生映射构建上，并让注册集合变成非确定的——同一组注册项在不同时刻遍历可能得到不同结果。

而下游系统（配置 key、网络包、序列化、发现统计）都隐含假设注册集合稳定确定，非确定注册直接动摇这些假设。

采用：收集一次、固化、运行时只读。注册只在一个明确的生命周期点（模组初始化）发生：内建与第三方依次把项交给各自 registry 的写入器，写入器填进内部 map，随后固化。这一不可变性不由运行期的 frozen 标志位来保证，而是由调用结构本身保证：`init()` 只在 `BiologyDictionary` / `BiologyDictionaryClient` 的静态初始化块里被触发一次（JVM cinit 保证），此后再无写入路径。

固化不妨碍运行时枚举：枚举读的是固化后的快照，想遍历多少次、在什么时机都可以，既便宜又确定。“支持未来任意运行时遍历”与“收集一次后固化”并不对立，而是同一设计的一体两面——固化正是安全枚举的前提。

被否决的方案：保留 re-walk。它把“项的集合”表达成“可重入执行的代码”，于是集合的语义被迫绑定到代码的执行语义上。集合应当是数据，不该依赖某段代码每次跑出什么。

## 决策二：第三方发现——loader 原生 entrypoint，平台层抽象

第三方模组如何让本模组知道“我要注册东西”？用各 loader 已有的 entrypoint 机制，而不是自己反射扫描全部模组找约定方法名。

手搓反射扫描看似简单，实则是劣化重造 entrypoint：没有类型（靠方法名字符串匹配）、没有声明（注册关系藏在代码里而非元数据里）、没有确定的加载顺序、一个模组抛异常容易连带炸掉整个发现过程。entrypoint 把这些都做好了：类型化、声明式（写在 loader 元数据里）、按加载顺序、可隔离失败，与 modmenu 等成熟集成是同一套范式。

本项目是 Architectury 多 loader 结构，发现机制按 loader 而异：Fabric 走 entrypoint 声明（loader 预解析、构造期可用），NeoForge 走 `@BiologyDictionaryPlugin` 注解扫描（`ModList.get().getAllScanData()` 聚合全部 mod 的字节码扫描结果，mod 发现阶段即完成、早于构造期）。两者都不依赖 classloader 资源枚举，把“发现”交给各 loader 的官方机制。loader 侧各有一个 `PluginRegistrar` 把发现的插件实例喂进 common 的缓冲，业务侧只看到一个统一的“收集全部插件”调用。

## 决策三：注册 API 形态——push（传入注册器，注册方调用）

注册方向框架声明自己的注册项，有两种自然形态：

- **push**：框架传入一个注册器（即现有 `Registrar`），注册方在其方法里反复调用注册器，返回 void；
- **pull**：注册方向框架返回一个待注册项的列表。

采用 push。理由：

1. **复用现有结构，几乎不引入新类型。** 现有 `Registrar` 接口和 `register0` 写入逻辑本就是 push 形态，直接作为第三方注册器暴露即可。pull 需要为每类注册项新增一个值类型承载注册参数，再把现有内建注册体全部改写成“构造值再装进列表”。

2. **编译期类型绑定由方法泛型天然给出。** widget、property、skill 的注册签名都用一个类型参数把“项的 class”与“对应的 factory/meta”绑定，编译期即可校验二者匹配。pull 的载体是值类型，而 Java 的 record 不能声明自身的类型参数，只能退化为通配类型、再用一个泛型静态工厂在构造点把绑定校验住——多一层，且仍不如方法签名直接。

3. **注册是一串带类型的调用，本就更像动作流而非静态数据。** 这一点与决策四的“注册只贡献、不删除”相配合：push 的语义就是“我把这些交给你的注册器”，恰好匹配。

两个一度被误归于 push 的缺点需要澄清：

- “每个注册点都要新建回调类”——这是 re-walk 的产物，不是 push 的固有成本。re-walk 下每个枚举消费方（init、配置、测试）各自造一个 `Registrar` 实现；固化之后消费方一律读快照，不再造实现。而 push 下注册方只是**消费**框架那唯一一个注册器，自己并不实现注册器。固化之后，无论内建还是第三方，注册侧都不产生新的回调类。

- “push 需要 per-plugin 缓冲与回滚来保证原子性”——不需要。直接写入 map（即现有 `init()` 的做法）就是常规行为。第三方注册中途抛异常时，try/catch 隔离、记录日志、继续下一个插件，已写入的部分保留即可。对一个出了 bug 的模组而言，部分注册是可以接受的终态，Forge 注册表在模组报错时同样不回滚。缓冲与回滚是为一个并不重要的性质而引入的多余机制。

## 决策四：禁用与移除——与注册分离

是否允许第三方“删掉”别人的注册项？不允许通过注册接口做。注册接口是 push 式的、只贡献的：注册方只能往里加自己的项。

把一个可变集合交给注册方任其增删，会让一个模组能静默移除另一个模组的项——既无归属也无审计，迭代中途修改、生命周期归属全成隐患。

若确实需要“隐藏某项”的能力，应提供独立的、显式的禁用通道，与注册分开：注册回答“我贡献什么”，禁用回答“我希望什么被隐藏”，两件事两个通道，各自归属清楚。这一通道是否复用项目现有黑名单的思路，属于实现细节，不在本设计层面固定。

## 决策五：注册顺序与确定性

跨模组的注册顺序需要一个确定规则，否则不同环境（开发/服务端/客户端、不同 loader）下项的相对位置会漂移，影响依赖顺序的展示（如 widget 渲染次序、entity order 的词典排列）。

规则：内建先行（保持现有内部序），随后第三方按 loader 声明顺序、并按模组 id 稳定排序；同一注册方内部按调用序。除非未来确有需求，不引入显式 priority 字段。

## 收敛点

设计的简洁性来自把所有写入收敛到少数几个 chokepoint：

- 每类 registry 唯一的 map 写入器（即 `register0`），内建与第三方共用；
- 注册只发生在各 registry 的 `init()`，而 `init()` 仅由静态初始化块触发一次（JVM cinit 保证）；不设运行期 frozen 标志，一次性由调用结构本身保证；
- 每类 registry 一个插件接口（`BiologySkillsPlugin` 等，各一个 register 方法）与平级 Registrar（均在 api 包）；Fabric 侧 entrypoint、NeoForge 侧 `@BiologyDictionaryPlugin` 注解扫描，由 `PluginLookup`（platform 层 `Platform.load` 桥）按插件类型发现，各 registry 在自己 init() 里 find → 派发，无中央缓冲。

第三方只见注册器与固化后的只读视图，看不到 registry 的内部 map。

## 实施顺序

1. 选定一个 registry（建议 `BiologySkills`，因为它当前存在运行时 re-walk，最能验证“收集一次 + 固化”）：抽出 map 写入器、引入固化、把 re-walk 改成读快照；
2. 在该 registry 上落地第三方注册入口（Fabric entrypoint / NeoForge `@BiologyDictionaryPlugin` 注解扫描）；各 registry 用 `PluginLookup.find(插件类型)` 发现并派发；
3. 验证无误后，把同一套骨架套到其余三类 registry；
4. 统一文档化第三方接入方式（entrypoint 声明 + 插件接口）。
