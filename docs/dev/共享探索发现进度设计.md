# 共享探索发现进度：需求分析与框架设计

> 状态：v7 已实施（分支 `dev-share-discovery`，2026-09-10）。2026-08-16 定稿，基于 mod 1.1.0 / MC 26.2。
> v2 推翻 v1 的"共享池持久化 + 双向合并迁移"方案，改为零持久化 + 派生视图；v3 把按需构建的视图升级为常驻全局发现统计；v4 把共享从 `DiscoverySource` 枚举剥离为记录字段并新增加载时迁移；v5 完成纯视图化：删去"发现时向其他玩家池落共享拷贝"的写时扩散路径，全局共享成为唯一的共享路径（查询派生 + 增量推送同一口径），并把统计的维护内聚到存储层；v6 严格拆分全局共享与主动分享的记录语义：前者只使用 `global`，从不读写 `shareChain`；v7 按 review 收敛：删除望远镜 no-op 轻反馈，简化全局呈现构造与客户端重同步，统一发现增量包，名字改为按需解析，并规范 record 字段顺序与命名。

## 1. 背景与目标

当前 `BIOLOGY_DICTIONARY` 发现策略下，发现进度严格按玩家隔离：每人一份独立的发现记录，互不可见。多人服务器希望"一人发现、全员解锁"：避免重复劳动，让发现成为社交事件；对末影龙这类全局唯一实体尤其有价值——它被击杀后其他玩家可能永远失去发现机会，共享进度让所有人的努力互相成就。

本需求新增一个服务端开关：**全局共享探索进度**。核心目标：

- 服务端可配置开启/关闭全局共享，支持运行时中途切换，切换零数据写入；
- 共享是**纯视图**：不向任何玩家池写共享拷贝，不新增持久化文件；全服发现情况由一份常驻内存统计承载，与开关无关；
- 每个人的发现行为与体验不变；他人的发现以"全局共享呈现"的形式临时可见，关闭即回落；
- 对现有插件 API、存档、网络协议保持向下兼容。

**术语**：全局共享（global sharing）= 本特性的自动视图共享，只由 `global` 标记；主动分享（active sharing）= 未来"玩家把特定生物页分享给他人"的独立特性，只由 `shareChain` 表达。全局视图的 `shareChain` 永远为空，两项特性之间不存在记录转换，本特性不实现主动分享。

## 2. 需求分析

### 2.1 功能需求

| # | 需求 | 说明 |
| --- | --- | --- |
| FR1 | 服务端开关 `discoveryGlobalShared` | 默认关闭；仅对 `BIOLOGY_DICTIONARY` 策略生效 |
| FR2 | 全局共享视图 | 开启时任一玩家的发现对全员立即生效（查询、解锁、总览权限判断） |
| FR3 | 运行时双向切换 | 开→关、关→开均可随时进行，切换零写入；关闭 = 视图回落，各自的池数据永远不受影响 |
| FR4 | 切换后在线玩家自动重同步 | 无需重进世界；任一方向都重建客户端缓存并全量拉取（非高频，简单优先） |
| FR5 | 发现事件全员推送 | 发现者体验完全不变（toast/挥手/高亮）；其他在线玩家收到通知与该发现的**全局呈现**（原始发现时间与来源），缓存即时更新 |
| FR6 | 记录携带发现者与全局标记 | 发现者 = 最初发现该生物的玩家，永不变；全局呈现只设置 `global=true`，`shareChain` 保持为空 |
| FR7 | 新玩家继承 | 开启期间加入的玩家通过派生视图直接继承全部共享进度，关闭后随口径回落 |

### 2.2 非功能需求

- **无损性**：共享不写任何数据，落盘的永远只有玩家自己的真实发现——无损是构造性的。
- **原子性**：两个玩家几乎同时发现同一类型时，全局只能产生一个"发现者"，后到者的发现自然 no-op。
- **确定性**：同一批持久化数据任意次派生，结果一致；同刻完全并列的相对顺序除外（遗留，§9）。
- **兼容性**：旧存档可读（加载时迁移）；旧版本读新档不报错（新字段被 codec 忽略）；插件 API 无签名破坏。
- **线程安全**：统计的派生与维护都在服务器线程（加载、put、查询路径天然串行）。
- **零切换成本**：开关翻转不产生任何存档写入；客户端只做一次缓存重建 + 全量拉取（非高频，简单优先）。

### 2.3 范围外（明确不做）

- `VANILLA_KILL` 策略的共享：其进度源于原版 per-player 统计，模组不持有、也不落盘该数据。
- `ALWAYS_UNLOCKED` 策略：天然全局，无需开关。
- 主动分享（书页分享）：与全局共享无关的独立特性，见 §10.2。
- 团队/权限粒度的分组共享（仅全局一档）。
- 共享进度的管理命令（查看/回滚/手动注入等运维操作）。
- 已发现类型上的轻反馈：v6 的"望远镜命中他人已发现类型"一次性 toast 已移除；发现动作本身 no-op，详情页的"发现玩家"行已足够表达信息。

## 3. 现状梳理

### 3.1 服务端策略与存储

- `DiscoveryManager` 挂在 `ServerWorldSession` 上（SERVER_STARTED、服务器线程），按 `discoveryStrategy` 配置实例化三种 `DiscoveryStrategy`，仅在模式变化时重建策略对象。
- `BiologyDictionaryDiscoveryStrategy` 通过 `SavedDataDiscoveryStorage`（`data/biologydictionary_discovery.dat`）持久化 `Map<玩家UUID, Map<EntityType, DiscoveryRecord>>`。`put` 用 `putIfAbsent` 保证"首见记录"不被覆盖。
- `DiscoveryRecord` 是不可变 record，字段顺序为：发现者 UUID `discoverer`、现实时间 `realTime`、游戏刻 `gameTick`、来源、维度、群系、坐标、天气、实体 UUID、实体 NBT 快照、全局标记 `global`、传播链 `shareChain`（分享者 UUID 列表）。NBT codec 与网络序列化集中在 `DiscoveryRecordSerializer`。

### 3.2 同步协议

| 方向 | 包 | 时机与用途 |
| --- | --- | --- |
| C→S | `RequestBiologyDictionaryDiscoveryFullPacket` | 客户端缓存重同步时主动拉全量（有效视图） |
| S→C | `ReplyBiologyDictionaryDiscoveryFullPacket` | 回复该玩家的全部有效视图记录 |
| C→S | `RequestDiscoveryIncrementalPacket` | 客户端本地预检（`clientCheck`）通过后发起，服务端权威复核 |
| S→C | `SendDiscoveryIncrementalPacket` | 新发现/全局共享：更新缓存；自己的记录走 toast + INTERACT 挥手 + 实体高亮；`global=true` 的记录走全局共享 toast（携带的发现者 `entityId` 被客户端忽略） |
| C→S | `RequestPlayerNamesPacket` | 客户端本地查不到名字时按需批量请求 UUID→名字 |
| S→C | `ReplyPlayerNamesPacket` | 回复名字表；查不到的 UUID 直接省略，客户端继续显示 UUID |
| — | KILL / KILLED_BY | 服务端 Mixin 直接触发，不走请求包 |

### 3.3 配置分发链

`ConfigsManager.onUpdated()` 是唯一的配置变更汇聚点，覆盖全部触发路径：启动加载、`/biologydictionary config reload`（专服）、Cloth Config 保存（单机/LAN）、远程同步（`ReplyServerConfigsPacket` 广播 YAML 后客户端反序列化）。它依次回调 `ClientWorldSession` 与 `ServerWorldSession` 的 `onConfigsUpdate`，再向远端玩家广播新配置。**这条现成的链路就是运行时切换的载体，不需要新增任何分发机制。**

### 3.4 客户端缓存

`ClientDiscoveryCacheManager` 按"服务器配置的策略模式"选择 `ClientDiscoveryCache` 实现；mode 或 global 任一变化都重建 delegate。`BiologyDictionaryClientDiscoveryCache` 持有网络包喂进来的记录表，构造函数请求一次全量；条目两类：自己的记录（`global=false`）与全局视图记录（`global=true`，临时）。

## 4. 关键设计决策

### D1. 开关形态：独立布尔项，而非新策略枚举值

否决 `DiscoveryStrategyMode` 增加 `BIOLOGY_DICTIONARY_SHARED`：共享与策略是正交概念；新枚举意味着复制一整个策略类、新增客户端缓存类，且把"共享开关"错误地升级为"进度体系切换"。布尔项跟随现有 `discoveryByXxx` 命名族，落点 `discoveryGlobalShared`（YAML 键 `discovery_global_shared`）。

### D2. 纯视图：共享不写盘、不拷贝、不扩散

全局共享**只有一条路径**：查询时派生。服务端有效视图 = 自己池 ∪ 全局统计（开关开启时）；客户端缓存里的全局条目标记 `global=true`，关闭时随缓存重建自然消失。每次发现向其他在线玩家推的也是同一口径的全局呈现（不是另一个版本的时间戳）。

v3/v4 曾实现"发现时向其他玩家池落共享拷贝（写时扩散）"，v5 删除，理由：

- 扩散的唯一增量收益是"关闭后已落盘的进度保留"，但该承诺只覆盖**有池**的玩家——开启期间入服的新玩家触发不了任何自己的真实发现、池永远不建、永远收不到拷贝，同一个开关对两类玩家的关闭语义完全不同，无法解释；
- 扩散贡献了全部的运行时成本：每次发现 O(玩家数) 次写 + O(玩家数) 份全量 NBT 包，存档按玩家数 × 类型数放大；
- 存在口径分裂：增量推"分享时刻"的拷贝、全量拉"原始时刻"的派生呈现，无池玩家两种口径都见过。

纯视图下所有人对称：开 = 看得到，关 = 看不到，各自的池数据永远不动。

### D3. 全局统计内聚在存储层

`GlobalDiscoveryStats`（每类型的全服发现顺序表，直接存 `DiscoveryRecord`，首个条目为最早记录（`earliestRecord`））不再由 `DiscoveryManager` 派生、策略追加，而是：

- `SavedDataDiscoveryStorage` 加载（Packed 构造）时 `deriveFrom(data)` 一次；
- `put` 成功且 `record.discoverer().equals(池主)` 时自动 append——"真实发现进统计"成为存储的自明不变量，与哪个策略、哪个 mode、怎么切换无关；
- 策略层只读 `storage.stats()`。

真实发现判定：发现者 == 池主（旧档记录的发现者在加载迁移时补齐为池主，见 D9）。排序：`gameTick` 升序，平手比 `realTime`；完全并列不再决胜（§9）。顺序表而非仅存最早记录：成本相同（记录按引用共享），为未来"第 N 个发现""时间线""服务器统计"预留。

### D4. 发现流程原子性：服务器线程串行决胜

开启期间一次发现事件的处理（全程服务器线程，天然串行）：

```text
onDiscovery(source, player, entity):
    if 有效视图(自己池 ∪ 全局统计) 已含该类型: return false     # 已被任何人发现
    写入发现者自己的池:  source 原样, 发现者=自己, 链为空（put 顺带进统计）
    if 开关开启: 向其余在线玩家推送 record.asGlobal()（时间/来源=原始, global=true, 链为空）
    向发现者推送自己的增量包（toast/挥手/高亮体验不变）
```

两人几乎同时发现：先被服务器线程处理的事件胜出成为"发现者"；后到者的有效视图已含该类型，事件自然 no-op。客户端侧因每连接包序保证，后到者的客户端会先收到共享推送、缓存已更新，预检都不会再发请求；即使预检用了旧缓存多发请求，服务端复核也会安全拒绝。

### D5. 全局呈现：记录的字段表达，而非 DiscoverySource

共享不占用 `DiscoverySource`（source 只承载真实发现方式）。全局呈现直接由统计最早记录 `record.asGlobal()` 得到：保留原始发现时间、游戏刻与 source，并设置 `global=true`。`DiscoveryRecord` 只保存发现者 `discoverer` UUID；名字不落盘、不进记录，由客户端 `PlayerNameCache` 按需解析（先查本地缓存与在线玩家，未知时批量请求服务端，服务端用 `ServerUtils` 从在线列表/usercache 解析），解析到之前显示 UUID。`shareChain` 专属于主动分享，全局共享不读取、不写入它，全局呈现的链始终为空。

### D6. 关闭语义：对称回落

- 服务端：查询口径从"自己池 ∪ 全局统计"回落为"自己池"；策略不因开关翻转而重建，每次调用动态读配置。
- 客户端：重建缓存并全量拉取（D7），关闭后自然只剩自己的记录；首页统计、总览权限即时回落。
- 反复开关 = 纯口径切换，零写入、无累积成本、无服务端过渡动作；关闭期间他人的新发现仍进统计，再次开启后立即可见。
- 所有人语义一致：保留的永远是"自己的真实发现"，没有"共享到你名下"这个概念。

### D7. 客户端重同步：一律重建

- mode 或 global 任一变化：`ClientDiscoveryCacheManager` 直接 `new` 对应策略的 `ClientDiscoveryCache`；`BiologyDictionaryClientDiscoveryCache` 的构造函数请求一次全量，服务端按当前口径回复有效视图。
- 不做"关闭方向纯本地丢弃"的特化：运行时切换不是高频场景，省一次网络不值得多维护一条路径；重建对 `ALWAYS_UNLOCKED` / `VANILLA_KILL` 也无副作用。
- `ClientDiscoveryCacheManager` 只比较 mode/global 两个值，其他配置刷新不触发重建。

### D8. 已发现类型上的发现动作：不再做轻反馈

v6 曾为"望远镜充满命中他人已发现类型"做一次性 toast；v7 删除。理由：这是为运行时切换/共享状态做的低频适配，玩家对已发现类型的发现动作保持静默 no-op；详情页的"发现玩家"行已承担信息职责。

### D9. 旧档迁移：加载时改写，业务读死

兼容层 `DiscoveryDataMigrator`（core.discovery.storage）在加载存档 NBT 时**就地迁移**为最新结构，并在 `SavedData` 上 `setDirty()` 使迁移结果写回盘。业务层只读最新结构。v5 只保留服务于真实发布格式的两条规则（幂等）：

- `source=telescope_observe` → `telescope`；
- `discoverer` 缺失或为 sentinel → 补为池主（pre-feature 记录没有该字段，统计派生依赖它；名字不再落盘；展示层解析不到时按规则回退）。

（v3 分支内开发期格式的迁移规则——`shared`/`global` source、`sharer` 字段——随纯视图化一并删除，那些格式从未发布。）

### D10. 有效视图的读取规则：自己的记录永远优先

`isDiscovered(P, X)` = P 的池中有 X **或** 全局统计含 X。`getRecord(P, X)` = P 池中自己的记录优先；缺失时返回统计最早记录的全局呈现。全量回复同理：自己池 + 统计补缺。开启前各自的发现记录在各自的词典里保持原样，他人的历史发现以全局呈现可见。

## 5. 详细设计

### 5.1 配置项

`Configs.ServerConfigs` 新增（紧邻 `discoveryStrategy`，YAML 键 `discovery_global_shared`）：

```java
/**
 * Whether discoveries are shared globally: anyone's discovery counts for
 * everyone while this is on. Pure view — nothing is written to the save,
 * and turning it off narrows the view back to each player's own records.
 * Only effective under the BIOLOGY_DICTIONARY discovery strategy.
 */
@ConfigEntry
boolean discoveryGlobalShared = false;
```

`@ConfigEntry` 反射机制自动接入 YAML 序列化、Cloth Config 界面与网络同步，无需额外接线。lang：配置项名称与说明。

### 5.2 服务端

- `SavedDataDiscoveryStorage`：持有 `GlobalDiscoveryStats`，加载即派生、`put` 自动维护（D3）；自定义 `Codec` 在 decode 里先跑迁移层再解析 `Packed` 并构建存储，迁移过则 `setDirty` 写回（D9）。
- `DiscoveryManager`：只剩 mode → 策略映射；`onConfigsUpdate` 对 global 翻转无动作。
- `BiologyDictionaryDiscoveryStrategy`：共享语义集中在这里——`isDiscovered` / `getRecord` / `getAllRecords` 按 D10 解析（开关关闭时退化为现有行为）；`tryDiscover` 按 D4 流程，推送的全局呈现直接由刚写入的 `record.asGlobal()` 构造，不再回查统计（有效视图判定保证它是该类型唯一的统计条目）。`RequestDiscoveryIncrementalPacket` 复核、全量回复经上述方法自然获得共享语义，包结构不动。

### 5.3 网络协议

| 包 | 变更 |
| --- | --- |
| `SendDiscoveryIncrementalPacket`（S→C） | 同时承载自己的发现与全局共享推送：字段 `entityId`、`entityType`、`record`；客户端按 `record.global()` 决定走自己的 toast/挥手/高亮还是共享 toast；共享推送的 `entityId` 是发现者实体，客户端忽略 |
| `RequestPlayerNamesPacket`（C→S） | 字段 `playerIds`（去重集合，服务端上限 64）；服务端用 `ServerUtils` 解析后回复 |
| `ReplyPlayerNamesPacket`（S→C） | 字段 `names`（UUID→名字）；查不到的 UUID 省略 |
| `Request/ReplyBiologyDictionaryDiscoveryFullPacket` | 结构不变，回复内容变为有效视图；不再附带玩家名字表 |
| `ReplyServerConfigsPacket` | 不变（YAML 自动携带新键） |

注：`DiscoveryRecord` 的网络序列化字段顺序已按 record 定义顺序调整（`discoverer` 在最前），旧版本客户端与服务端混连会在 record 解析处错位——模组要求双端同版本，不承诺跨版本协议兼容。名字不进 record、也不落盘，只按需请求。

### 5.4 客户端

- `ClientDiscoveryCacheManager`：mode 或 global 变化都重建 delegate；`BiologyDictionaryClientDiscoveryCache` 构造函数请求一次全量（D7）。
- `BiologyDictionaryClientDiscoveryCache`：构造函数请求全量；`onDiscovery` 只做 `isDiscovered` 预检 + `clientCheck`，无望远镜特判。
- `PlayerNameCache`：客户端名字缓存。`get`（私有）只查本地 cache → `ClientUtils.getPlayerName`；`getDisplayName`（公有）不请求，未知返回 UUID；`getDisplayNameOrRequest`（公有）未知时用 `computeIfAbsent` 把 UUID 作为临时值写入 cache 并请求一次，返回该临时值；`request(list)`（公有）批量请求，未知项同样写临时 UUID 占位。服务端回复 `putAll` 覆盖所有值（包括已存在的名字），widget 下一帧即可看到。
- `EntityDiscoveryRecordWidget`：每帧渲染时重新构建行；`playerText` 用 `getDisplayNameOrRequest` 按需取名字，未知 UUID 只请求一次（占位缓存阻止重复请求）；服务端回复后下一帧自动刷新。第一行是发现相关——自己的记录“发现玩家：XXX”；全局共享“发现玩家：XXX（全局共享）”；主动分享“发现玩家：XXX（分享者：YYY）”；无法解析时“发现玩家：（无数据）”；之后依次是邂逅方式、现实时间、游戏时间、相遇地点、详细坐标、当地天气。
- `DiscoveryToast`：统一标题“发现新生物！”；实体名行按来源追加注解：全局共享“（全局共享；发现者：X）”，主动分享“（分享者：X）”。名字用 `getDisplayNameOrRequest`：本地有就用，没有就发一次请求并显示临时 UUID——toast 的 Component 构建后不再变化。
- 首页“已发现/总数”统计基于客户端缓存，共享模式下自动反映有效视图。
- lang：`zh_cn` / `en_us` 同步（配置项、toast、widget 行）。

### 5.5 离线与后加入玩家

- **离线玩家**：无需任何处理——统计常驻且实时，回归后拉取即得完整视图。
- **开启期间新加入的玩家**：全量拉取即继承全部共享进度；关闭后随口径回落为自身池内容（可能为空）。不为 join 增加回填钩子（回填 = 写时扩散的死灰复燃）。

### 5.6 对外 API 与插件兼容

- `ServerDiscoveryApi` / `ClientDiscoveryApi`：签名全部不变。javadoc 语义补充：全局共享模式下"该玩家的发现"= 该玩家的有效视图。插件零破坏。
- `DiscoverySource` 及第三方注册流程：不变，共享不占枚举位。
- 共享呈现的 `discoverer`/`global` 字段插件可直接读取；其 `shareChain` 保证为空。
- 名字解析是纯展示层：`ClientUtils` / `ServerUtils` 的名字查询与 `PlayerNameCache` 与 discovery 无关，插件可复用。
- `docs/plugin-api.md` 增补共享语义说明。

## 6. 边界情况与风险

| 场景 | 处理 |
| --- | --- |
| 两人几乎同时发现同类型 | 服务器线程串行决胜（D4），仅一人成为发现者，另一人 no-op |
| 客户端旧缓存导致多发请求 | 服务端权威复核 no-op，无副作用；包序保证客户端随后收到共享推送 |
| 开关反复翻转 | 纯口径切换：服务端零动作、零写入；客户端每次重建 + 全量拉取（非高频）；统计常驻且始终最新 |
| 名字解析 | 客户端按需请求；服务端从在线列表/usercache 解析；未知显示 UUID |
| 同现实毫秒 + 同游戏刻的完全并列 | 排序先后跨重启不保证稳定，记为遗留（§9）；不影响共享语义，最早记录并列时任取其一 |
| 旧档升级 | 加载时迁移（telescope 改名、发现者补池主）并 `setDirty` 写回；业务层只读最新结构（D9） |
| 存档体积 | 不变——纯视图零额外写入（v4 的"按玩家数放大"问题随写时扩散一并消失） |
| 网络广播量 | 每次发现 O(在线人数) 份通知包（含全局呈现）；亲友服规模可忽略，大型公共服建议关注 |
| 共享 toast 打扰 | 原版 toast 单队列串行展示，多人高频发现时会积压；当前定位亲友服可接受，未来可加节流/可配置关闭 |
| 公共服务器玩法影响 | 一人推进度全员解锁，可能不符合竞争型服务器预期——配置说明提醒按需开启 |
| `VANILLA_KILL` / `ALWAYS_UNLOCKED` 下开关无效 | 策略层只在 `BiologyDictionaryDiscoveryStrategy` 消费该标志 |
| LAN 局域网开服 | 配置广播跳过 owner 的现有逻辑不冲突；owner 作为普通玩家参与共享 |
| 全局唯一实体（末影龙等） | 共享后所有人获得记录——本需求的典型动机场景 |

## 8. 测试要点

1. 单机反复开→关→开：每次变化都重建缓存并全量拉取；开启时有效视图与统计一致，关闭后只剩自己的记录。
2. 关闭期间 A 的发现仍进统计；再次开启后 B 无需任何操作即可看到。
3. LAN 双人：A 发现 → B 收到 toast、词典即时更新；B 看到的详情时间为 A 的原始发现时刻、来源为 A 的真实来源；A 体验与现状一致（挥手/高亮）。
4. 原子性：构造两人同 tick 对同类型触发发现，仅一人成为发现者，另一人 no-op。
5. 旧档升级：telescope_observe 改名、发现者补池主，`setDirty` 写回后盘上为新格式；二次加载不再迁移（幂等）。
6. 开启期间新玩家进服：全量继承视图；关闭后进度回落为自身池内容。
7. 望远镜命中已共享类型：静默 no-op（无 toast）；详情页第一行发现玩家：自己的记录显示自己、全局共享显示“XXX（全局共享）”、主动分享显示“发现玩家：XXX（分享者：YYY）”；名字每帧从 cache 刷新，解析到前显示 UUID /（无数据）；toast 只查本地、查不到显示 UUID（不刷新）。
8. `VANILLA_KILL` / `ALWAYS_UNLOCKED` 策略下开关无效。
9. 专服 `/biologydictionary config reload` 中途翻转，在线玩家不重进世界即完成重同步。
10. 首页发现统计与总览权限（`allowOverviewForUndiscoveredEntities=false`）在共享模式下口径一致。

## 9. 遗留问题

- **完全并列记录的排序稳定性**：运行时两人几乎同时（同 tick、同现实毫秒）发现同类型时，先后由服务器线程处理顺序决定，该顺序不落盘；重启后统计只按（游戏刻, 现实时间）排序，完全并列的多条真实记录其相对顺序、以及最早记录的选取，可能与上一会话不同。注：开启共享期间不会新产生并列真实记录（后到者 no-op），并列只能来自关闭期间或开启前的历史数据。影响仅限展示层面；发现者身份已由记录字段固化，重启不会翻转。若未来需要精确稳定的名次，再补确定性决胜（如按发现者 UUID）或落盘顺序号。

## 10. 未来扩展

### 10.1 全服发现进度查看（按需拉取）

玩家查看各生物的全服发现进度（顺序表、谁在第几个发现、时间线等）。方案是**请求-回复快照**，不是常驻实时同步：

- 新增一对 C→S / S→C 包：单类型请求回复该类型顺序表，总览请求回复全量统计，与现有 `RequestEntityOverviewPacket` / `RequestBeehiveInfoPacket` 同模式；
- 服务端直接从常驻统计切快照，零额外维护；数据挂在打开的 screen 生命周期上，不进 discovery cache，关界面即丢；
- 不做增量广播：浏览型 UI 打开即拉、天然新鲜；
- 统计与共享开关解耦（D3），因此**关着共享也能看**——纯信息特性。

### 10.2 主动分享（书页分享）

主动分享是独立需求，不属于本设计。其记录只通过 `shareChain` 表达；全局共享只通过 `global` 表达。主动分享不得读取、转换或持久化全局视图，全局共享也不得读取或构造传播链，两项功能分别设计和实现。
